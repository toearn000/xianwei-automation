# 架构与技术细节

本文档记录「仙位挑战自动化」引擎（`src/zmws.py`）的架构决策、识别算法、
坐标体系与容错设计。所有阈值均来自实战截图标定，标定数据保留在代码注释中。

## 1. 总体架构

系统分为四层，单向依赖，每层可独立替换：

```
调用层    CLI 子命令（rect/shot/click/badges/state/scan/clickscan/mode/config/xianwei）
           └ 全自动模式：整个战斗循环下沉脚本层，零上层往返
决策层    画面状态机 analyze() + 策略选择（high_power / low_power）
识别层    像素采样 region() + 颜色判定（is_red / is_orange / is_green）+ 亮度 bright()
传输层    WebBridge daemon HTTP API（evaluate / screenshot / cdp）
执行层    真实 Edge 浏览器（CDP Input.dispatchMouseEvent）
```

关键取舍：

- **为什么不用 OCR / 模板匹配**：游戏文字小、字体抗锯齿、弹窗有半透明遮罩，
  OCR 误判率高且慢；模板匹配对分辨率与缩放敏感。而按钮/徽章的**颜色特征
  极其稳定**（红章恒红、主按钮恒橙），颜色占比统计是 O(n) 的 numpy 向量化
  运算，单张截图全状态判定在毫秒级完成。
- **为什么不注入游戏页面**：页游反外挂高危，注入 JS 有被检测风险；外部
  观察 + 外部操作让游戏完全感知不到自动化存在。
- **为什么是单文件 742 行**：部署目标是一台日常使用的 Windows 机器，
  单文件 + 三个常见依赖（numpy/pillow/requests）把环境风险降到最低。

## 2. 画面状态机

`analyze()` 对一张截图做**单趟判定**，输出 6 态之一。判定顺序即优先级，
利用「弹窗会压暗背景按钮」这一视觉事实做互斥：

```
            ┌──────────────┐
            │  截图输入     │
            └──────┬───────┘
                   ▼
        victory 确定按钮亮橙？ ──是──► victory（胜场+1，点确定）
                   │否
        rankup 确定按钮亮橙？ ──是──► rankup（点确定，可能在胜利后叠加出现）
                   │否
        drop 绿色按钮亮？ ──────是──► drop（点「继续游戏」，绝不点「前往宝库」）
                   │否
        4 张卡挑战按钮全亮橙？ ──是──► opponent_list
                   │                  （附带 badges 检测 + 按策略算好 target）
                   │否
        确认弹窗：左橙确定 + 右绿取消同时亮？ ──是──► confirm
                   │否
                   ▼
               unknown（重试 2 次后存图停机，交回人工）
```

两个设计细节：

- `confirm` 判定放在 `opponent_list` **之后**：弹窗压暗挑战按钮使其不满足
  「全亮」，因此确认弹窗天然不会误判成对手列表。
- **上下文防呆**：`confirm` 状态只在上一步动作是「刷新」时才自动点确定；
  来源不明的确认弹窗一律停机（`unexpected_confirm`），因为付费操作的确定/
  取消位置固定但语义随场景变，盲点代价高。

## 3. 视觉识别算法

### 3.1 颜色判定（向量化布尔掩码）

```python
红（碾压章/红字）:  R>=120 且 R-G>=70 且 R-B>=70
橙（主按钮）:       R>=180 且 80<=G<=190 且 B<=110 且 R-B>=120
绿（继续游戏）:     G>=120 且 G-R>=30 且 G-B>=40
```

每个检测点取一个比例采样框（如红章区域半宽 0.02、半高 0.025），统计掩码
占比与阈值比较：

| 检测目标 | 阈值 | 标定依据 |
|---|---|---|
| 碾压红章 red_frac ≥ 0.30 | 0.30 | 实战样本 4 卡红章占比 56.6%~58.9%，阈值留足余量 |
| 亮橙按钮 orange_frac ≥ 0.30 且 亮度 ≥ 55 | 0.30 / 55 | 被弹窗压暗的背景亮度 28~33，亮按钮 107~116 |
| 绿色按钮 green_frac ≥ 0.20 | 0.20 | 实战校准（2026-09-15，green_frac 0.45） |
| 对手战力红字 red_frac ≥ 0.05 | 0.05 | 黄字卡恒 0.000，红字卡 0.086~0.231 |

「颜色占比 + 平均亮度」双条件缺一不可：占比区分颜色，亮度区分「按钮亮着」
与「按钮被弹窗半透明遮罩压暗」。

### 3.2 为什么阈值可审计

代码注释中保留了每组阈值的标定日期、样本来源（截图名）、统计量
（median RGB、范围、占比分布），新画面误判时可以按同样流程重新标定——
这在低战力账号验收中实际发生过一次（新增 `confirm` 状态）。

## 4. 坐标体系

游戏运行在页面 iframe 内，三个坐标系叠加：

```
比例坐标 (fx, fy)          ← 标定时使用的唯一形式，与分辨率无关
    │  CSS px = (r.x + fx·r.width, r.y + fy·r.height)
    ▼  r = iframe.getBoundingClientRect()（每次执行现取）
CSS 像素
    │  物理像素 = CSS px × dpr（实测 dpr=1.5）
    ▼
截图物理像素
```

铁律：

- **禁止硬编码绝对像素坐标**。窗口可被用户随时缩放/移动，每次点击、每次
  采样前都重新 `evaluate` 取 rect 与 dpr。
- 点击走 CDP `Input.dispatchMouseEvent`（pressed + released 成对，同坐标，
  `button:"left"`, `clickCount:1`），用 CSS 像素；截图读像素时乘 dpr。
- 离线分析支持 `--rect "x,y,w,h,dpr"` 直接注入坐标系，同一份 `analyze()`
  代码服务在线执行与离线回放测试（5 种历史截图回放判定全对即靠此机制）。

## 5. 容错设计

| 风险 | 对策 |
|---|---|
| 随机弹窗吞掉点击 | 每次点击前先判定画面状态；弹窗各自有自动关闭路径 |
| 段位提升在胜利后叠加出现 | 状态机把 rankup 与 victory 作为独立状态循环处理，不假设出现次序 |
| 画面抖动/截图时机不佳 | `unknown` 状态允许重试 2 次（间隔 3 秒），仍不识別则存图停机 |
| 付费刷新成本递增失控 | 刷新次数上限可配置（默认 15）；`confirm` 弹窗上下文防呆 |
| 无限循环 | 全局步数上限（80 步）硬兜底，超限停机并输出 SUMMARY |
| OpenBLAS 多线程内存崩溃 | `os.environ.setdefault("OPENBLAS_NUM_THREADS","1")` 在 numpy 导入前生效 |
| 失败结算画面未标定 | 判 `unknown` 停机交回人工——**刻意的安全行为**，宁可漏报不可误操作 |

## 6. 性能设计

- **合并子命令**：`scan` = 截图+判定一次进程调用；`clickscan` = 点击+等待+
  截图+判定一次调用。原则：「能合并成一次 clickscan 的绝不拆成四步」。
- **循环下沉**：`xianwei` 子命令把整个 5 场战斗循环放进单个 Python 进程，
  期间零上层调度往返，这是 53.4 秒成绩的主要来源。
- **本地计数**：剩余次数开局读一次，每场 victory 本地减 1，不为读数额外
  截图（底部状态栏数字在结算画面期间是旧值，本来就不该在循环中读）。
- **结构化收尾**：最后一行输出 `SUMMARY {json}`（ok/reason/wins/refreshes/
  events/duration_s/last_shot），供调度方机器可解析地判断成败并归档证据。
